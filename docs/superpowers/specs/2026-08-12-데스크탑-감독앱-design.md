# priorcase 데스크탑 감독 앱 — 설계

>

> **2026-08-13 v1 구현 완료** — 계획은

> 대신한다. 구현하면서 스펙과 달라진 것 넷:
>
> 1. **검토의 [맞다] 는 `review --outcome good` 이 아니라 `prior reviewed <id>`**
>    다. outcome 을 쓰면 회고 큐가 그 노트를 영영 제외한다

>    접힌 채로만 두면 내용의 72~93%가 영영 안 보인다.
> 3. **메뉴바는 합계 하나**다. 종류별로 내면 회고가 상설 백로그라 배지가 영구히
>    켜져, 스펙이 세운 "늘 떠 있으면 무시한다" 를 스스로 어긴다.
> 4. **회고에 [노트 열기] 를 뒀다.** 요약 한 줄(30~139자)로 "결과적으로 좋았나"
>    를 판정하는 것은 확인이 아니라 짐작이다.

## 1. 무엇을 만드는가

**기계가 한 일을 사람이 승인·정정·판정하는 자리.**

사람이 무언가를 적는 곳이 아니다. 이 제품의 원칙이 *"자동으로 기록해 준다"* 이므로,
사람에게 남는 일은 **확인·검증·판정** 셋뿐이고 그 셋은 전부 타이핑이 아니라 클릭이다.

→ [[priorcase-결정-데스크탑앱-감독표면-입력아님-2026-08-12]]

### 왜 필요한가 — 실측

| | 기계가 한 일 | 사람이 해야 할 일 | 지금 |
| --- | --- | --- | --- |
| 확인 큐 | "여기 결정이 있는 것 같다" 표시 | 맞나 확인 | **27건 누적** (2026-08-12) |
| 검토 큐 | 판별기가 노트를 만듦 | 맞나 검증 | 만든 것 1건, **근거 날조 있었음** |
| 회고 큐 | 결정을 기록 | 결과 판정 | `outcome` 98건 중 판명 **2건 (2%)** |

수명 관리 2% 가 핵심 신호다. `prior review --outcome good` 은 처음부터 있었다 —
안 쓰인 이유는 **되돌아볼 순간을 아무도 만들어 주지 않아서**다. 기록은 훅이 자동으로
시키는데 회고는 시키는 사람이 없다. CLI 는 상주하지 않으므로 구조적으로 못 하는 일이다.

> **개인 도구로 바뀌어도 이 근거는 그대로다.** 앱을 올렸던 근거의 절반은
> "팀 도입의 첫 마찰" 이었고 그건 사라졌다. 남은 절반 — 감독 표면 — 은 혼자 쓸 때도
> 값이 있고, 특히 회고는 **먼저 말을 거는 것이 없으면 안 된다.** 위 2% 는 혼자
> 쓰면서 난 숫자다.

## 2. 형태

**메뉴바 상주 + 조용한 알림.**

- 항상 떠 있다. 아이콘에 **숫자만** 붙는다 (`확인 3 · 회고 2`).
- **푸시 알림을 보내지 않는다.** 먼저 말을 거는 도구는 지워지고, 앱이 지워지면
  자동 기록까지 같이 잃는다.
- 사람이 클릭할 때 보여 준다.

이 프로젝트가 이미 같은 판단을 여러 번 했다 — 팀 이식성 경고는 볼트가 git 일 때만,
색인/git 경고도 그럴 때만 낸다. 소음은 사람에게 경고를 무시하는 법을 가르친다.

## 3. 볼트가 여럿이다 — 앱에 미치는 영향

**앱에는 cwd 가 없다.** 메뉴바에 상주하므로 "지금 어느 프로젝트에서 일하는가" 를
모른다. 그런데 CLI 와 훅은 cwd 로 볼트를 고른다 — `prior queue --json` 도 지금은
그렇다. 그대로 두면 앱은 **셸이 마지막으로 있던 자리의 볼트**를 보게 되고, 그건
사람이 예측할 수 없다.

**앱의 큐는 선언된 볼트를 전부 덮는다.** 각 줄이 자기 볼트를 달고 온다.

| 큐 | 지금 | 앱을 위해 필요한 것 |
| --- | --- | --- |
| 확인 | 상태 디렉토리 하나(볼트 무관) · 줄마다 `domain` | `domain` → 볼트 이름을 붙인다 |
| 검토 | 승격 원장 하나(볼트 무관) · 줄마다 `domain` | 같음 |
| 회고 | **Layout 하나 = 볼트 하나만 본다** | 볼트를 순회해야 한다 |
| 상태 | `doctor` 는 이미 전부 본다 | `queue` 도 맞춘다 |

**왜 전부 덮나.** 회수는 볼트 경계를 지킨다 — A 프로젝트에서 일할 때 B 볼트의 결정이
에이전트 컨텍스트에 뜨면 안 되기 때문이다. 그런데 **감독은 회수가 아니다.** "확인할
것이 3건 있다" 는 내 전체에 대한 사실이고, 볼트마다 앱을 따로 열게 하면 감독 표면이
아니라 파일 브라우저가 된다.

**공유 볼트가 새지 않는다.** 확인·검토 큐의 원본은 내 상태 디렉토리이고, 회고 큐의
방아쇠는 **내 회수 이력**이다 — 남이 그 볼트에 쓴 결정은 내가 회수한 적이 없으면
안 뜬다.

> ~~**⚠ 선행 작업**: `retro.Due` 가 볼트 하나만 본다~~ — ✅ 2026-08-13.
> `retro.AllDue` 가 볼트를 순회하고, `confirm`·`review`·`retro` 줄마다 `vault` 가
> 붙는다. 실측: cwd 를 바꿔도 회고 큐가 45건으로 같다 (전에는 0건 vs 43건).

## 4. 화면

### 4.1 확인 큐

미확인 구간을 하나씩. 발췌와 시그널을 보여 주고 두 버튼.

```
2026-08-11 · priorcase (personal 볼트) · 시그널 결정·선택
────────────────────────────────────────────────────────
에이전트: 측정이 하나를 확실히 골라냅니다…
(발췌 6~8줄)

비슷한 기존 결정
   118  priorcase-결정-체크포인트정리-중립성만-…
    33  priorcase-결정-판별기-상한과-포기-카운터-…

  [결정이다 → 기록한다]     [아니다 → 지운다]
```

- `[아니다]` → `prior pending --resolve <id>`
- `[결정이다]` → `prior promote <id>`. 사람이 본문을 쓰지 않는다(원칙).
  판별기가 노트를 만들면 그 결과가 검토 큐로 넘어간다.

**한 줄에 보여 줄 것** (2026-08-12·13 실측에서 나온 것):

| | 왜 |
| --- | --- |
| 날짜 · 도메인 · **볼트** | 어느 프로젝트의 언제 일이고 어디에 쓰일 것인가 |
| 시그널 | **없을 수 있다.** 판별기가 있으면 필터를 건너뛴다(D9) — 27건 중 2건이 그랬다 |
| 발췌 | 실측 880B~4.9KB. 한 화면에 안 들어가는 것이 절반이다 |
| **비슷한 기존 결정 (점수 포함)** | "이미 남겼나" 를 가장 빨리 답한다 |
| **판별기 실패 횟수 · 포기 여부** | 포기한 줄은 자동으로 다시 안 온다 — 기다리면 안 된다 |

비슷한 결정 줄이 실제로 판단을 바꾼다. 큐를 손으로 비워 보니 **"이 구간이 결정인가"
보다 "이 결정이 이미 남았나" 가 훨씬 자주 묻는 질문이었고**, 7건 중 **4건이 그
대조만으로** 판정됐다.

**앱은 그 대조로 단정하면 안 된다.** 점수를 같이 보여 주고 사람이 고른다 — 회수는
언제나 무언가를 돌려주므로, 일치가 없는 발췌도 1위가 나온다(실측: 진짜 일치 65점과
가짜 1위 54점이 겹쳤다).

→ [[priorcase-결정-확인큐-볼트대조-판정은안한다-2026-08-12]]
→ [[priorcase-결정-판별기-상한과-포기-카운터-2026-08-12]]

### 4.2 검토 큐 — 가장 중요한 화면

판별기가 만든 노트를 **발췌와 나란히** 놓는다.

```
발췌 (판별기가 본 것)          │  판별기가 쓴 노트
──────────────────────────────┼──────────────────────────
사용자: canonlog 로 가자        │  ## 근거
에이전트: 확인했습니다…         │  canonlog 는 판례집의
                              │  라틴어 표현으로 …   ← 대화에 없다

  [맞다]   [고친다]   [지운다]
```

**이 화면이 앱의 존재 이유에 가장 가깝다.** ③ 자동 승격이 만든 유일한 노트에
근거 날조가 있었고(없는 어원을 지어냄), 그것을 사람이 우연히 발견했다. 지시문에
제약을 넣었지만 **그건 완화이지 보장이 아니다** — 판별기는 LLM 이다.

**실제로 한 번 더 필요했다.** 2026-08-13 에 판별기가 작업 도중의 설계를 결정으로
기록했는데, 그 설계는 뒤에 검증으로 반증되어 되돌려졌다. 볼트에 뒤집힌 결정이
`active` 로 남아 있었고 큐 정리 중에 우연히 발견했다. **자동 기록은 결정이
검증되기 전에 잡는다** — 이 화면이 그 구조적 위험을 받는 자리다.

`[고친다]` 는 예외적으로 텍스트를 다룬다. 원칙("사람이 적지 않는다")과 충돌하지
않는다 — 새로 쓰는 것이 아니라 **틀린 것을 고치는** 일이다.

옛 원장 줄에는 발췌가 없다(2026-08-12 이전). 그때는 **"대조할 발췌가 없다" 고
말해야 한다** — 없는 것을 조용히 안 보여 주면 사람은 노트만 보고 맞다고 누른다.

→ [[priorcase-결정-승격발췌-원장에남긴다-2026-08-12]]

### 4.3 회고 큐

```
2026-08-09 · priorcase (personal 볼트) · 재회수 4회
"결정 노트에 스키마 판을 붙이고 더 새 판의 노트는 읽고 회수하되 고치지 않는다 — …"
                                          — zesty <…>

  [좋았다]   [나빴다]   [아직]
```

방아쇠: **재회수 2회 이상 `OR` superseded**, 그리고 `outcome: pending` 인 것만.
최소 경과 기간 없음.

→ [[priorcase-결정-회고방아쇠-재회수2회-기간없음-2026-08-12]]

**`[아직]` 을 고른 뒤 언제 다시 묻는가** — 같은 방아쇠가 **한 번 더** 울릴 때까지
안 묻는다. 즉 재회수 카운트가 현재값+1 이 될 때. 시간을 쓰지 않는 이유는 회고
방아쇠와 같다: 규칙이 둘이 되면 "왜 안 뜨지" 를 설명할 수 없다.

### 4.4 상태

`prior doctor` 가 내는 검사를 그대로. 큐가 셋 다 비었을 때 앱이 보여 줄 것이
이것뿐이므로 **비어 있어도 반드시 채운다.**

볼트가 여럿이면 **볼트마다 한 줄씩** 나온다 (`doctor` 가 이미 그렇게 한다).
하나만 보면 나머지가 깨져 있어도 초록불이 뜨고, 그 볼트를 쓰는 프로젝트에서
일할 때에야 드러난다.

배선이 안 됐으면 여기서 `prior init --apply` 를 대신 실행한다. **새 기계에
옮길 때가 그 자리다** — 혼자 쓰더라도 기계는 바뀐다.

## 5. 아키텍처

```
┌─ Tauri 2 앱 ────────────────┐
│  UI (웹뷰)                   │
│  Rust 측: 프로세스 실행       │
└──────────┬──────────────────┘
           │ prior queue --json      (읽기, 폴링)
           │ prior pending --resolve │
           │ prior promote <id>      │ (쓰기)
           │ prior review --outcome  │
           │ prior init --apply      │
           ▼
      prior (Go 단일 바이너리)
           ▼
      볼트 여럿 (마크다운) · ~/.local/state/priorcase
```

**앱은 파일을 직접 다루지 않는다.** frontmatter 방출·스키마 검증·색인 갱신이 두
벌이 되면 한쪽만 고쳐진 채로 남는다 — 이 프로젝트가 감사에서 죄목으로 든 것이
정확히 그것이고 arch 테스트로 막아 둔 것도 그것이다. 앱은 **또 하나의 어댑터**다.

볼트가 여럿이 되면서 이 규칙이 더 중요해졌다. **어느 볼트에 쓸지는 도메인이 정하고
그 규칙은 `capture` 안에 있다** — 앱이 경로를 조립하기 시작하면 그 규칙이 둘이 된다.

→ [[priorcase-결정-데스크탑앱-Tauri-CLI경유-사건기반회고-2026-08-12]]
→ [[priorcase-결정-어댑터경계-테스트강제-2026-08-07]]

### 5.1 읽기 — `prior queue --json`

이미 있다(2026-08-12 구현). 세 큐와 상태를 **한 스냅샷**으로 준다.

```json
{
  "confirm": [{"id","domain","vault","when","signals","excerpt",
               "fails","gave_up","similar":[{"stem","path","summary","score"}]}],
  "review":  [{"id","domain","vault","at","path","excerpt"}],
  "retro":   [{"stem","date","domain","vault","summary","author","reason","hits"}],
  "health":  [{"name","level","detail","fix"}],
  "warnings": ["…"]
}
```

- 네 번 따로 부르면 그 사이에 훅이 돌아 **서로 어긋난 큐**가 나란히 보인다.
- `level` 은 `ok|warn|fail|unknown` 문자열이다. 정수면 앱이 `0 == 정상` 을 외워야
  하고 상수 순서가 바뀔 때 **조용히 뒤집힌다.**
- 빈 큐는 `[]` 다. `null` 이면 앱에서 "아직 안 왔다" 와 "할 일이 없다" 가 구별되지 않는다.
  중첩 배열(`signals`·`similar`)도 마찬가지다.
- `warnings` 는 없으면 **키 자체가 빠진다.** 있으면 큐가 불완전하다는 뜻이다.

계약은 `internal/adapter/cli/queue_test.go` 가 못 박는다. **손으로 만든 값만 보면
배선 누락을 못 잡는다** — 실제로 `similar` 를 만들고 호출부에 안 붙인 적이 있고,
`similar: null` 이 나가서야 드러났다. 명령을 실제로 돌리는 테스트가 따로 있다.

`vault` 는 omitempty 가 아니다 — 빈 문자열은 "볼트를 모른다"(설정 오류)는 사실이고,
키까지 빠지면 앱이 그것과 "필드를 모르는 옛 버전" 을 구별하지 못한다.

### 5.2 갱신 주기

**폴링.** 앱이 뜰 때, 창을 열 때, 그리고 30초마다.

`prior queue --json` 이 실측 1.0초다(결정 98건). 회고 큐는 매번 계산하고 캐시하지
않는다 — 상태를 하나 더 두면 볼트를 손으로 고쳤을 때 틀어진다.

파일 감시(fsnotify)를 쓰지 않는 이유: 볼트와 상태 디렉토리 양쪽을 봐야 하고,
그래도 회고 큐는 재계산해야 한다. 얻는 것이 적다.

**1.0초는 결정 98건 · 볼트 하나 기준이다.** 볼트가 늘면 그만큼 곱해진다.
볼트가 10배가 되거나 노트가 10배가 되면 재회수 계산이 O(n²) 로 는다(각 노트마다
전체 회수). **그때는 재고 캐시를 다시 본다 — 지금 추측으로 캐시를 넣지 않는다.**

### 5.3 쓰기

전부 `prior` 명령이다. 실패하면 **조용히 넘어가지 않는다** — 큐에서 사라졌는데
볼트에 반영이 안 되면 사람은 답한 줄 안다.

## 6. 오류 처리

| 상황 | 앱의 동작 |
| --- | --- |
| `prior` 를 못 찾음 | 설치 안내 화면. 큐 대신 그것만 보여 준다 |
| `prior queue` 가 0 아닌 종료 | stderr 를 그대로 보여 준다. 빈 큐로 그리지 않는다 |
| `warnings` 가 비어 있지 않음 | 큐 위에 배너. **"할 일 없음" 으로 그리면 안 된다** |
| 쓰기 명령 실패 | 그 줄을 큐에 되돌리고 이유를 보여 준다 |
| 볼트 하나가 깨짐 | 그 볼트의 `health` 를 `fail` 로. **나머지 볼트의 큐는 그대로 보여 준다** |
| 설정이 깨짐 | `health` 의 `fail` 항목을 크게. 큐는 비운다 |

**빈 큐와 실패를 구별하는 것이 이 표의 전부다.** 이 시스템은 모든 부품이 실패해도
대화를 막지 않도록 설계됐고, 그 대가로 고장이 정상과 구별되지 않는다. 앱이 그 구별을
못 하면 앱도 같은 병에 걸린다.

## 7. 테스트

- **계약**: `queue_test.go` 가 이미 키 목록을 고정한다. 앱은 그 형태만 신뢰한다.
- **앱 쪽**: `prior` 를 가짜 스크립트로 바꿔 각 오류 상황을 재현한다
  (없음·0 아닌 종료·깨진 JSON·warnings 있음·볼트 하나만 깨짐). 표 6행이 그대로 테스트 6개다.
- **수동**: 큐가 셋 다 빈 상태와 셋 다 찬 상태를 눈으로 본다. 빈 상태가 "고장난
  것처럼" 보이지 않아야 한다.

## 8. 배포

**혼자 쓰는 것이 기본이고 한두 명이 같이 쓸 수 있다** — 그 선에서 정한다.

`.app` 배포는 **애플 공증을 되살린다** — npm 경로가 없앤 비용이다.
그리고 `tauri build` 의 **DMG 번들링이 비대화형 세션에서 멈춘다**(omni 실측).
`.app` 까지는 된다.

**v1 은 로컬 빌드로 간다.** 공증 없이 `.app` 을 만들어 직접 쓴다 — 내 기계에서는
`xattr -d com.apple.quarantine` 한 번이면 된다. 한두 명에게 줄 때가 오면 그때 공증을
다시 본다. **지금 공증을 붙이면 쓰지도 않을 인프라에 시간을 쓴다.**

**CLI + 훅을 대체하지 않는다.** 앱은 그것을 감싼다 — 둘 중 하나를 고르는 것이 아니다.

## 9. 범위 밖

- **빠른 기록(수동 입력)** — 원칙에 어긋난다. 사람에게 적으라고 하는 순간 다른
  메모 앱과 같아진다.
- **볼트 브라우저(검색·타임라인)** — Obsidian 이 이미 하고, 회수는 CLI·에이전트가
  이미 한다. 실측된 구멍을 하나도 안 메운다.
- **팀 상태 서버** — **안 만든다.** 같이 쓰는 사람이 한둘일 때 서버는 값보다 비용이
  크다. 탭 자리도 비워 두지 않는다 — 안 쓸 자리를 열어 두면 설계가 그쪽으로 휜다.
- **볼트 편집·이동** — 앱에서 프로젝트를 다른 볼트로 옮기지 않는다. 설정 파일이
  정본이고, 그 이동은 위키링크·색인을 다시 맞춰야 하는 일이다.
- **화면 녹화·음성** — 보류. 호스트 파서를 붙이고 남은 구멍을 잰 뒤에 판단한다.
