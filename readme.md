# 세컨드브레인 훅 안정화 및 개선 작업 지시서

Obsidian 볼트에서 운용 중인 "세컨드브레인" 훅(결정 기록 저장/회수 시스템)을 진단·안정화하고, 그 위에 구조 개편과 기능 개선을 적용하는 작업이다.

---

## A. 작업 원칙 (전 단계 공통)

1. **기존 구현 기반 개선**: 처음부터 새로 만들지 않는다. 기존 코드를 읽고 개선한다. 단, Phase 0 진단 결과 구조적 결함이 크다고 판단되면 근거와 함께 재작성을 제안하고 승인을 받는다.
2. **승인 게이트**: 아래 두 지점에서는 반드시 결과를 보고하고 사용자 승인을 받은 후 진행한다.
   - Phase 0 완료 시: 진단 결과 + 수정 계획
   - Phase 2 진행 전: 파일 이동·변경 대상 목록
3. **파괴적 작업 금지**: 기존 문서를 이동·수정할 때는 반드시 `_archive/`에 원본을 백업한 후 진행한다.
4. **작업 순서**: Phase 0 → 1 → 2 → 3~8 → 9(검증). 안정화(1)가 기능 개선보다 우선이다.

## B. 환경 및 전역 제약

- **볼트 절대 경로**: `/Users/zesty/Documents/Obsidian Vault`
  - 경로에 공백이 있으므로 모든 스크립트에서 반드시 따옴표 처리한다.
  - 각 스크립트 상단에 경로 상수 하나로 통일해 정의한다.
- **파일 시스템 직접 접근으로 통일**: Obsidian MCP, Local REST API를 사용하지 않는다. 기존 구현에 이들 의존이 있으면 파일 직접 접근으로 전환한다. (Obsidian 앱이 꺼져 있어도 동작해야 한다.)
- **에러 처리 공통 규칙** (모든 훅 스크립트):
  - 실패 시 대화를 방해하지 않도록 `exit 0`으로 종료한다.
  - 실패 내역은 볼트의 `logs/hook-errors.log`에 `타임스탬프 + 단계 + 원인` 형식으로 기록한다.
  - 매 실행의 처리 경로(스킵/성공/실패 및 단계)를 `logs/hook-trace.log`에 한 줄씩 남긴다.
- **LLM 호출이 있는 훅**: 타임아웃을 명시 설정하거나 백그라운드 처리로 전환해 대화 지연과 훅 타임아웃(기본 60초) 킬을 방지한다.

## C. 구현 구조: `cb` 단일 CLI 원칙 (오픈소스 "casebook" 전환 대비)

이 시스템은 추후 오픈소스 프로젝트 **casebook**(CLI 명령 `cb`)으로 전환될 예정이다. 개인용 단계부터 아래 구조를 따른다.

- **단일 진입점**: 모든 로직(기록/회수/INDEX/롤업)은 볼트의 `scripts/cb` 단일 CLI 스크립트에 서브커맨드로 모은다. 로직을 훅 스크립트 여러 개에 흩뿌리지 않는다.
  - `cb capture` — 결정 기록 생성/갱신 (스키마 검증, related 연결, INDEX 재생성 포함)
  - `cb recall <query>` — 결정 검색. `--format inject` 옵션으로 훅 주입용 출력
  - `cb index` — INDEX.md 재생성
  - `cb review` — 기존 결정의 outcome/회고/supersedes 갱신
  - `cb rollup` — 작업 로그 주간 요약 (Phase 7)
- **훅 = 얇은 래퍼**: 각 훅 스크립트는 이벤트별 입력 파싱과 `cb` 호출만 담당하는 몇 줄짜리 래퍼로 유지한다. 훅에 비즈니스 로직을 두지 않는다.
- **설정 격리**: 볼트 경로 등 개인 설정은 `cb` 상단 상수(추후 설정 파일로 분리 가능)에만 존재하게 한다.

## Phase 2. 볼트 구조 개편 (이동 목록 승인 후 실행)

1. **`decisions/` 통합**: 루트에 `decisions/` 폴더를 만들고 전 프로젝트의 결정 기록을 통합한다. 프로젝트 구분은 하위 폴더가 아니라 **파일명 접두어 + frontmatter의 `domain` 필드**로 한다.
2. **기존 문서 마이그레이션** (`omni/decisions/` → 루트 `decisions/`):
   - 파일명이 이미 `<domain>-결정-*` 규약을 따르므로 파일명은 유지한다.
   - frontmatter만 새 스키마(Phase 3)로 보강한다 (`summary`, `status`, `outcome` 등 누락 필드 추가).
   - 날짜가 파일명에 없는 문서는 **파일 생성일 기준**으로 날짜를 붙여 리네임한다.
   - **이동·변경 대상 목록을 먼저 보여주고 승인받은 후** 실행하며, 원본은 `_archive/`에 백업한다.
3. **메타 문서 정리**: 루트의 `00-세컨드-브레인-*` 메타 문서들은 `_meta/` 폴더로 이동한다.
4. **"무제" Base 파일**: 목록만 보고하고 처리 방법은 사용자가 정한다.

## Phase 3. 결정 기록 스키마

### 파일명 규약

```
decisions/<domain>-결정-<slug>-YYYY-MM-DD.md
예: omni-결정-셸전략-Tauri단일-2026-08-02.md
```

- `<domain>`은 프로젝트 접두어 (`omni`, `mesh`, `occ`, `draft00`, `synth`, `noi` 등). `00-볼트-네이밍-규약` 문서를 읽고 기존 접두어 목록과 일치시킨다.
- 특정 프로젝트에 속하지 않는 결정은 접두어 `common`을 사용한다.
- **파일명 접두어와 frontmatter `domain`의 첫 번째 값은 반드시 일치**해야 하며, Stop 훅이 파일 생성 시 이를 강제한다.
- 여러 프로젝트에 걸친 결정은 주된 프로젝트를 접두어로 쓰고 나머지는 `domain` 배열에 추가한다.

### frontmatter

```yaml
type: decision
date: YYYY-MM-DD
domain: [] # 첫 값 = 파일명 접두어. [omni], [mesh, occ] 등
summary: "" # 한 줄 요약. 회수 시 이것만 주입되므로 필수
status: active # active / superseded / regretted
outcome: pending # pending / good / bad
supersedes: ""
related: [] # 다른 프로젝트 결정과의 위키링크
tags: []
source_session: ""
```

### 본문 섹션

`결정 / 근거 / 고려한 대안 / 예상 리스크 / 회고`
(기존 문서들이 "결정 / 근거" 구조를 쓰고 있으므로 이를 유지·확장한다.)

### INDEX

- `decisions/INDEX.md`: `날짜 | domain | summary | status | outcome | 링크` 테이블.
- 결정 파일 변경 시 frontmatter 파싱으로 자동 재생성한다 (한 결정 = 한 줄).

## Phase 4. 기록 루프 (세션 중간 기록 중심)

**전제**: 사용자는 세션을 종료하지 않고 compact를 반복하며 하나의 세션을 길게 이어서 쓴다. 따라서 "세션 종료 시 일괄 저장" 모델은 트리거가 오지 않는다. 기록은 (A) 세션 중간의 에이전트 주도 기록을 주 경로로, (B) PreCompact 훅을 안전망으로 하는 이중 구조로 설계한다.

### 4-A. 에이전트 주도 기록 (주 경로)

- 결정 기록을 **에이전트가 세션 중 직접 실행할 수 있는 명령**으로 만든다: `cb capture` (C 섹션의 단일 CLI). 필요 시 이를 호출하는 슬래시 커맨드 `/decision`을 함께 제공한다.
- `cb capture` 책임: 스키마 검증(파일명 접두어 = `domain` 첫 값), INDEX 관련 결정 탐지 후 `related` 위키링크 연결, 파일 생성/갱신, INDEX 재생성.
- 에이전트가 "언제 기록할지"를 판단할 수 있도록 CLAUDE.md에 기록 트리거 규칙을 명시한다 (Phase 8 참조). 판단 기준 예: 아키텍처·기술 선택, 전략 변경, 대안 비교 후 채택, 기존 결정의 번복.
- `update` 시나리오(기존 결정의 `outcome` / 회고 / `supersedes` 갱신)는 `cb review`로 처리한다.

### 4-B. PreCompact 훅 (안전망)

compact 직전은 맥락이 요약되며 소실되는 시점이므로, 에이전트가 놓친 결정을 여기서 건져낸다. 아래 순서의 **사전 필터 구조**로 구현한다. LLM 호출은 최후 단계다.

1. 체크포인트 상태 파일(`logs/capture-checkpoint.json` 등)을 읽어 **마지막 처리 지점 이후의 transcript 구간만** 대상으로 한다 (증분 처리)
2. 대상 구간의 턴 수가 임계값(예: 4턴) 미만이면 체크포인트만 갱신하고 종료
3. 대상 구간을 ripgrep으로 검사해 결정 시그널 키워드가 없으면 체크포인트 갱신 후 종료
   - 키워드: `결정`, `선택`, `하기로`, `대신`, `전략`, `포기`, `변경`, `채택` 등
   - 스크립트 상단 배열로 정의해 조정 가능하게 한다
4. 통과 시에만 `claude -p --model claude-haiku-4-5` 호출
   - 입력은 대상 구간의 **사용자 발화 전체 + 각 assistant 턴의 마지막 문단만 발췌**해 전달한다
5. 판별 프롬프트에 `INDEX.md`를 포함시키고 JSON으로 응답받는다:
   ```json
   { "action": "create" | "update" | "none", ... }
   ```

   - INDEX 대조로 **4-A에서 이미 기록된 결정과의 중복을 방지**한다 (중복이면 `none` 또는 `update`)
   - `create` / `update`의 실제 쓰기는 `cb capture` / `cb review`를 재사용한다 (로직 이원화 금지)
6. 완료 후 체크포인트를 갱신한다. 실패 시 조용히 종료하고 `logs/hook-errors.log`에만 기록한다.
7. PreCompact는 auto / manual compact 모두에서 동작해야 한다.

### 4-C. Stop 훅 처리

- Claude Code의 Stop 훅은 세션 종료가 아니라 **매 턴 응답 완료 시** 실행된다. 기존 구현이 Stop에서 전체 transcript를 판별하고 있었다면 이것이 중복 판별·토큰 낭비·불안정의 원인일 수 있으므로 Phase 0 진단에서 확인한다.
- 개편 후 Stop 훅은 사용하지 않거나, 사용할 경우 체크포인트 기반 증분 + 키워드 필터 통과 시에만 동작하는 초경량 구조로 한정한다. 기본 방침은 **미사용(4-A/4-B로 대체)** 이다.

## Phase 5. 회수 루프: UserPromptSubmit 훅 (LLM 호출 금지)

- 검색 로직은 `cb recall <query>`로 구현하고, UserPromptSubmit 훅은 stdin의 prompt에서 키워드를 추출해 `cb recall --format inject`를 호출하는 얇은 래퍼로 만든다.
- **순수 스크립트로만 구현한다. LLM을 호출하지 않는다.**
- `cb recall`의 검색 방식:
  - 1차 필터: 파일명 접두어 glob (`<domain>-결정-*`)
  - 2차 필터: frontmatter(`domain` / `tags` / `summary`) 및 본문 ripgrep 매칭
- 상위 **최대 3건**을 다음 형식으로 stdout에 출력한다 (전문 주입 금지, summary와 경로만):

  ```
  [과거 결정 참조]
  - <date> <summary> (status/outcome) → <경로>
  ```

- `regretted` 또는 `outcome: bad` 건이 포함되면 마지막에 한 줄 추가:
  > "위 결정 중 아쉬운 결과로 기록된 건이 있음. 유사 선택 시 회고를 먼저 읽고 수정안을 제안할 것."
- 매칭 없으면 아무것도 출력하지 않는다.
- 검색 로직은 `cb recall` 내부에서 **별도 함수로 분리**해 추후 임베딩 검색으로 교체 가능하게 한다.
- 검색 제외 대상: `_archive/`, `_meta/`, `logs/`, `99-*-작업-로그*` 원본

## Phase 6. SessionStart 훅 (compact 후 복구 포함)

- `INDEX.md`에서 **최근 결정 10건의 summary 라인 + `status: active` 목록**만 주입한다.
- 전체 **30줄 이내** 상한.
- SessionStart는 신규 세션뿐 아니라 **compact 후 재개 시에도 발화**된다(`source: compact`). compact로 소실된 결정 맥락을 직후에 재주입하는 복구 지점이므로, `startup` / `resume` / `compact` 모든 source에서 동작하도록 설정한다.

---

## Phase 7. 작업 로그 롤업 (토큰 절감)

- 각 프로젝트의 `99-*-작업-로그`를 주 단위로 요약하는 **수동 실행 명령 `cb rollup`** 으로 구현한다 (`claude -p`, haiku 사용).
- 결과는 각 프로젝트 폴더의 `98-작업-로그-요약.md`에 append한다.
- 원본은 보존하되 회수 훅 검색 대상에서 제외한다.
- 실행 방법을 문서화해 알려준다. **자동 스케줄링은 하지 않는다.**

## Phase 8. CLAUDE.md 계층화

### 볼트 루트 CLAUDE.md (짧게, 다음 내용만)

- 볼트 절대 경로와 "볼트 작업은 파일 직접 접근으로 한다" 명시
- 볼트 구조, 파일명 규약(`<domain>-결정-<slug>-날짜`), decisions 스키마 요약, `common` 접두어 규칙
- 행동 규칙:
  - **결정이 내려지면 세션 종료를 기다리지 말고 그 자리에서 `cb capture`(4-A)를 실행할 것.** 기록 대상: 아키텍처·기술 선택, 전략 변경, 대안 비교 후 채택, 기존 결정의 번복. 단순 구현 디테일이나 시행착오는 기록하지 않음
  - 주입된 `[과거 결정 참조]`가 있으면 해당 문서를 읽고 답변에 반영할 것
  - 새 결정이 과거 결정을 대체하면 `cb review`로 `supersedes`와 이전 문서 `status`를 갱신할 것
  - 결과가 판명된 결정은 `cb review`로 `outcome`과 회고를 갱신할 것
  - 다른 프로젝트의 관련 결정이 있으면 `related`에 위키링크를 걸 것

### 프로젝트별 컨텍스트

- 상세 컨텍스트는 각 폴더의 `00-개요` 문서에 유지하고 **루트 CLAUDE.md에는 넣지 않는다.**

## Phase 9. 검증 시나리오 (전부 통과해야 완료)

- [ ] **1. 세션 중간 기록**: 세션 중 결정이 내려진 직후, 에이전트가 스스로 `cb capture`(4-A)를 실행해 `decisions/`에 규약에 맞는 파일명으로 생성 + INDEX 갱신 확인 (세션 종료 없이)
- [ ] **2. PreCompact 안전망**: 결정이 포함됐지만 4-A로 기록되지 않은 상태에서 `/compact` 실행 → PreCompact 훅이 해당 결정을 생성하는지 확인
- [ ] **3. 중복 방지**: 4-A로 이미 기록된 결정이 있는 상태에서 `/compact` 실행 → PreCompact가 INDEX 대조로 중복 생성하지 않는지(`none` 또는 `update`) 확인
- [ ] **4. 사전 필터 스킵**: 결정 시그널 없는 잡담 구간만 있는 상태에서 `/compact` 실행 → 사전 필터에서 스킵되어 LLM 호출 없이 종료. `hook-trace.log`로 어느 단계에서 스킵됐는지 확인
- [ ] **5. 증분 처리**: compact를 2회 연속 실행 → 두 번째 실행이 체크포인트 이후 구간만 처리하는지 확인
- [ ] **6. compact 후 재주입**: compact 완료 후 SessionStart(`source: compact`)가 INDEX 요약을 재주입하는지 확인
- [ ] **7. 회수 주입**: 기존 결정과 같은 domain의 프롬프트 입력 → `[과거 결정 참조]` 주입 확인 (장기 세션 중간에도 동작)
- [ ] **8. common 접두어**: 프로젝트 무소속 결정 → `common` 접두어로 생성 확인
- [ ] **9. bad outcome 경고**: 결정 하나를 `outcome: bad`로 수동 변경 후 유사 프롬프트 → 수정 제안 문구가 나오는지 확인
